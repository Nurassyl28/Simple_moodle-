# SECURITY — читать до написания кода

Этот проект работает с чужими паролями и оценками. Ошибка здесь — это не баг,
это утечка персональных данных, за которую отвечает автор проекта лично.
Правила ниже не обсуждаются.

## Пароли

1. Пароль студента используется **ровно один раз** — для обмена на токен.
2. Пароль **не сохраняется** нигде: ни в БД, ни в файле, ни в логе, ни в кэше,
   ни «временно», ни «зашифрованным». В модели данных поля для пароля нет.
3. Обмен на токен делается только по HTTPS.
4. Форма входа честно говорит студенту, что происходит: «мы войдём в Moodle
   от твоего имени, чтобы показать твои данные; пароль не сохраняется».

## Токены

1. Токен = секрет уровня пароля. Даёт доступ к оценкам и данным студента.
2. Хранить **только зашифрованным** (ключ шифрования — не в коде, в переменной
   окружения/секрет-менеджере).
3. Токен **никогда** не попадает: во фронтенд, в URL, в ссылки на файлы, в логи,
   в сообщения об ошибках, в аналитику.
4. Файлы Moodle отдаются студенту через прокси-эндпоинт бэкенда, который сам
   подставляет токен на своей стороне. В ссылке, которую видит браузер, токена нет.
5. Студент может «выйти» — тогда токен удаляется из БД.

## Уроки, оплаченные на этом проекте

- Токен всплывает в неожиданных местах: в логах локального сервера, в скриншотах.
  Поэтому логи с токенами недопустимы, а при отладке токен маскируется.
- «Failed to fetch» из браузера напрямую в Moodle — это защита CORS, и это правильно.
  Вывод: в Moodle ходит бэкенд, не браузер.

## Разрешение (нетехническая, но обязательная защита)

Даже с идеальным кодом публичный сервис, который собирает пароли/данные студентов
SDU **без ведома университета**, — недопустим. До запуска на реальных пользователях:

1. Обратиться в IT-отдел SDU (шаблон в `docs/it-request.md`).
2. Получить явное разрешение или официальный доступ к API.
3. Только после этого — Фаза 2.

Прототип на самом авторе (свой токен, свои данные, локально) под это правило не
попадает и разрешён.

## Данные

- Оценки, курсы, дедлайны студентов — персональные данные. Минимизировать: хранить
  только то, что нужно для работы, не собирать «на всякий случай».
- Дать возможность удалить аккаунт и все данные.
